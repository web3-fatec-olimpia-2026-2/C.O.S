# ADR 001 — Proteção do campo `perfil`

## Contexto
O sistema baseia o seu controle de acessos rigoroso em quatro perfis de utilizador: Administrador, Prestador, Comum e Premium. Se o campo `perfil` no modelo `Usuario` aceitasse qualquer texto (uma *string* livre), poderíamos ter registos com valores inválidos (por erros de digitação, como "adminstrador" em vez de "ADMIN", ou valores maliciosos). Isso quebraria a lógica de permissões no backend, podendo conceder acessos indevidos a funcionalidades críticas ou corromper a auditoria.

## Decisão
Decidimos proteger esse campo utilizando o parâmetro `choices` nativo do ORM do Django e definindo um `default` restritivo. O campo foi implementado como `models.CharField(max_length=20, choices=PERFIS_CHOICES, default='COMUM')`. Dessa forma, o próprio modelo valida se a entrada pertence estritamente à tupla de perfis autorizados antes de gravar na base de dados. 

## Alternativa descartada
Validar os perfis apenas no formulário da tela de criação de utilizadores (via `<select>` no HTML) ou na *view* de submissão. Esta alternativa foi descartada porque não protege o sistema caso um utilizador seja criado por outros caminhos, como pelo painel nativo do Django Admin, pelo *shell* do terminal (scripts de importação) ou por uma futura integração via API. O requisito exige expressamente que a segurança e as permissões não sejam controladas apenas pela interface.

## Consequência
O modelo de dados passa a proteger-se de forma centralizada; é impossível criar um utilizador com um perfil fora das regras de negócio sem gerar um erro de validação. O sistema fica protegido contra elevação de privilégios acidental (já que o default é o perfil "COMUM", que apenas tem permissões de leitura). Em contrapartida, se precisarmos de adicionar um quinto perfil no futuro, teremos de alterar o código na classe do modelo e gerar uma nova migração (*makemigrations*) na base de dados.
